# LEGO Blockly — notes for Claude

Browser app (Chrome) that programs LEGO hardware from Blockly blocks. No build step: plain ES modules, Blockly loaded as a global.
Hardware is reached through Web Bluetooth / Web Serial / WebUSB / WebSocket. Claude cannot reach any hardware: the owner tests in the browser and pastes console output.

## Layout
- `index.html`: connect dropdown (`<option value="SPIKE">…`), run / stop buttons.
- `main.js`: imports every driver and block file, the connect `switch` (`case "SPIKE": … connectLegoSpike3()`), run-program wrapper, STOP logic.
- `device/deviceManager.js`: `DeviceManager` (names like `Prefix1`, `getDeviceByName`, `connectXxx()` per driver, wake lock).
- `device/DeviceXxx.js`: one driver class per hardware family.
- `blocks/lego_blocks.js`, `generators/lego_generators.js`, `toolbox/toolbox.js`: block definitions, JavaScript generators, toolbox.
- `service-worker.js` (asset list + network-first), `version.js` (bump `LEGO_BLOCKLY_VERSION` to force a cache refresh).
- `SketchArduino/<Name>/<Name>.ino`: Arduino sketches for the ESP32 bridges / boards.
- Docs: `README.md`, `LEGO_BLOCKLY_CONNECTIONS.md` (neither mentions SPIKE or ESP32io yet).

## Checking work without hardware
- Sketches compile with the IDE's own CLI (owner: Arduino IDE 2.3.10, esp32 core 3.3.12, NimBLE-Arduino 2.5.1):
  `"/c/Program Files/Arduino IDE/resources/app/lib/backend/resources/arduino-cli.exe" compile --config-file /c/Users/Lenovo/.arduinoIDE/arduino-cli.yaml --fqbn esp32:esp32:esp32 --build-path <scratchpad> SketchArduino/<Name>` (`esp32:esp32:esp32s3` for the S3).
- Types used in function signatures of a `.ino` must live in a header next to it: the Arduino IDE writes the function prototypes above any type defined in the `.ino`.
- Blocks can be tested headless: `npm install blockly@12.4.1` in the scratchpad, stub the globals (`registerFieldColour`, `javascript = { javascriptGenerator }`, `window.addEventListener("load")`), run `lego_blocks.js` / `lego_generators.js` with `vm.runInThisContext`, build each toolbox entry with `Blockly.serialization.blocks.append` and run its generated code against a fake device.

## Adding or extending a driver (checklist)
1. `device/DeviceXxx.js`: `export class Xxx { constructor(name, manager) … async connect() … async disconnect() }`. Use the manager hooks the other drivers use: `manager._allocateName(prefix)`, `updateDeviceEntry`, `appendLog`, `_removeDevice`, and `handleDeviceLost` on unexpected disconnect.
2. `deviceManager.js`: import the class, add `async connectXxx()` (copy `connectLegoLPF2`: try/catch, `_addDevice`, `_freeName` on failure).
3. `main.js`: `import "./device/DeviceXxx.js"`, a `case` in the connect switch. `index.html`: an `<option>`.
4. STOP: `main.js` has an if/else chain over device methods (`portsOff`, `stopMotor`, `stopAllMotors`…). A new driver must be reachable from it (SPIKE and LPF2 use `stopAllMotors`).
5. `service-worker.js`: add the file to `ASSETS`.
6. Blocks (below), then docs.

## Blocks, generators, toolbox conventions
- One dropdown helper per family at top level of `lego_blocks.js`, filtering `window.deviceManager.devices` by `d.constructor.name` (see `getLPF2Dropdown`, `getSpike3Dropdown`). Empty list returns a `['No …','NONE']` placeholder.
- Block JSON arrays live inside the `window.addEventListener("load", …)` handler; first argument of every block is the `DEVICE` dropdown (`"options": getXxxDropdown`). Prefix block types per family (`lpf2_*`, `spike_*`).
- Port / mode / axis choices are small constant blocks (`lpf2_ports`, `spike_stopmode`…) used as toolbox shadows so users can replace them with variables. Every value input gets a default shadow in `toolbox.js` (math_number, text, or a constant block). Toolbox categories are nested: family → Input / Output / Message / Misc.
- Generators (`javascriptGenerator.forBlock["type"]`): statements wrap in `{ shouldStop(); const dev = deviceManager.getDeviceByName("…"); if (!dev) throw new Error("Device lost"); await dev.method(...); }`. Reporters return `[ "(await deviceManager.getDeviceByName(\"…\").getX(port))", ORDER ]`. Always provide fallbacks for empty inputs.
- Generated code runs in an async wrapper in `main.js` with `deviceManager`, `getDeviceByName`, `shouldStop`. STOP sets `window.stopRequested`; any long wait inside a driver must poll it and return.

## File format
- The project's working files use CRLF line endings (blocks, generators, toolbox, main.js, index.html and, since the last checkout, the SPIKE driver and helper). Check with `git ls-files --eol` / `od -c` before patching and keep each file's style.
- Git stores LF; on a machine without `core.autocrlf`, `git diff` looks like every line changed (use `--ignore-cr-at-eol`).

## SPIKE hub (88016 Robot Inventor on SPIKE firmware, Hub OS 1.8.x) — `DeviceLegoSpike3.js`
- BLE service `fd02`; framing is COBS-style with XOR 3 (LEGO "spike-prime-docs"), CRC32 over data padded to a multiple of 4.
- Sensor values (motors, colour, distance, force, tilt, battery) come from the hub's DeviceNotification stream, no program needed. The colour message is 10 bytes on this firmware (the docs say 9).
- Programs: StartFileUpload must be `name + 0x00 + slot + crc` (NOT a padded 32-byte name, or the hub silently stores it wrongly). The file name is `program.py`.
- Motor/matrix/beep output needs the resident MicroPython helper (`SpikeMotorHelper.js`, uploaded on demand with the "Upload Motor Helper" block, default slot 19). It talks over the message tunnel (`hub.config["module_tunnel"]`, undocumented by LEGO). Replies look like `id,ok` / `id,done,X,(0,)` / `id,err,…`. Bump `SPIKE_MOTOR_HELPER_VERSION` and the `VER` in the Python when the helper changes; users must re-upload it.
- Hub buttons (left / right) are NOT in the BLE notification stream. Helper v3 polls `hub.button` and sends `0,btn,<L|R>,<1|0>` events; the driver keeps the state (`buttonState(side, mode)`), the `spike_button` block reads it. Needs the helper running (re-upload it after a driver update: `SPIKE_MOTOR_HELPER_VERSION` is 3).
- Verified on hardware (owner's tests): connect, notifications, upload + start, tunnel both ways, motor blocks, LED matrix, beep, hub light, set hub name, start/stop slot programs, upload program, message send/read/wait, most input blocks. Not yet verified: hub buttons (helper v3, `button.pressed(button.LEFT)` from the SPIKE 3 docs), force sensor (owner has none), colour 'reflection' (an undocumented extra byte in the colour message), watchdog.

## ESP32io (generic ESP32 I/O board) — `DeviceESP32io.js`, class `ESP32io`, sketch `SketchArduino/ESP32io/`
- Non-LEGO board for switches, sensors, LEDs, servos, H-bridges and encoders wired on an ESP-WROOM-32 (ESP32-S3 compiles but is untested). Connect value `ESP32io` ("ESP32 Generic IO").
- Transport: Nordic UART Service (`6e400001…`), one text line per command, same commands on USB Serial 115200 (the full list is at the top of `ESP32io.ino`). `[id] CMD args` → `[id] OK [data]` / `[id] ERR msg`; id 0 = fire-and-forget (only errors are answered). The board pushes `V pin=value …` for inputs when they change (every 20 ms at most) plus all inputs every second, and `L msg` logs.
- Driver: `request()` waits for OK (setup commands); outputs use `send()` without waiting and skip repeated values; input getters read the pushed values instantly. `request(cmd, timeout, onOk)` runs `onOk` while the OK line is parsed: `_cfg` and `resetCount` use it to drop values that arrived before the OK (an old count from the previous run made "wait until encoder ≥ 360" pass at once).
- Picker filter: advertised manufacturer data `FF FF 'L' 'B' 'i' 'o'` (Chrome `manufacturerData` filter), so the board is found whatever its name; `namePrefix: "ESP32io"` is the fallback. BLE name (default `ESP32io`) is saved in the ESP32 flash by `NAME` / `setHubName()`, shown after the next disconnect; the Device Manager name is the BLE name + number (`RobotA` → `RobotA1`, a trailing digit gets `_`).
- The Blockly program does the setup (`CFG` blocks) on every run. The board releases every pin when the PC connects or disconnects; released outputs are driven to their "off" level (LOW, or HIGH for inverted digital outputs), never left floating, so an H-bridge cannot start a motor.
- A port is named by its first pin: H-bridge = IN1 (2-pin boards: DRV8833 / MX1508 (1508S) / L9110S / ZK-5AD) or EN (3-pin boards: L298N / L293D / TB6612), encoder = A pin. Board names map to HB2 / HB3 in `ESP32IO_HBRIDGES`; a new board only needs a name there and in the block dropdown.
- Pins (WROOM-32): 4, 13, 14, 16-19, 21-23, 25-27, 32, 33 I/O; 34, 35, 36, 39 input only, no internal pull-up/down; analog in = ADC1 only (32-39); DAC 25, 26. Strapping, flash and UART0 pins are excluded. The same table exists 3 times: `PIN_CAPS` in the sketch, `ESP32IO_CAPS_WROOM32` in the driver, `ESP32IO_PINS_WROOM32` in lego_blocks.js. Block pin dropdowns use the fixed WROOM-32 list (`esp32ioPinOptions()`): a list built from the connected board (`CAPS`) needs a custom dropdown first, because Blockly silently replaces a saved pin that is not in the current list.
- Encoders use the PCNT hardware (8 units on WROOM-32, 4 on S3), extended to 32 bits. X4 / X2 count both edges so contact bounce cancels; X1 counts A edges only while B is LOW (+1 rising, −1 falling) for the same reason. `ppr` and `gear` live in the driver only (degrees = count × 360 / (ppr × mult × gear)); `reverse` flips the sign.
- Servos: a 360 servo takes a speed (-100..100, 1500 µs = stop), a 180 servo an angle; `servoAngle` / `servoSpeed` throw on the wrong type (the angle block on a 360 servo used to stop it silently).
- H-bridges: HB2 = one input PWM, the other LOW (fast decay), brake = both HIGH; HB3 = EN PWM + IN1/IN2 direction, brake = IN1 = IN2 = HIGH. Defaults 20 kHz (HB2) / 1 kHz (HB3). The L9110S ignores the brake (both inputs HIGH = outputs off): it can only coast. Brake stops faster but does not hold the position (position hold = closed-loop step 2). A geared motor needs a minimum power to start (N20 rated 3-6 V on 4.8 V: about 60 %): PWM gives power × supply volts on average, so this is the motor, not a bug.
- Closed-loop motors (firmware v2, step 1 of 3, console only, no blocks yet): `LINK <hb> <enc>` / `linkMotor(16, 18)` links an H-bridge port to an encoder port (at most PCNT units / 2 motors: 4 on WROOM-32, 2 on S3). The loop runs in `loop()` every 5 ms (`motorsTick`): speed from the count change over 20 ms, setpoint ramp (0 → 100 % in 200 ms), feedforward `ks + (100 − ks) × sp / top` + PI with gains computed from the calibration (lambda tuning), anti-windup, "wrong way" guard (stops with `M <pin> ERR`). Speeds are encoder counts/s in the motor direction (count × dir) on the board; the driver works in % of the calibrated top speed. `RUN` 0 = brake. `SET` / `STOP` / watchdog / releasing either port go back to open loop.
- Calibration (`CAL` / `calibrateMotor(16)`, about 4 s, the motor turns up to full power): slow power ramp until the encoder moves (start power, direction), full-power step (response time `tau` = 63 % point − 10 ms measurement lag, top speed), a middle power (friction `ks` from the two points). Saved in NVS per motor pin (`cal16`, with the encoder mode so X1/X2/X4 changes rescale `top`); ppr / gear / reverse are JS-only and need no recalibration. Uncalibrated motors refuse `RUN`. `MPAR` / `setMotorCalibration()` sets it by hand (the future "motor profile" block), `MPAR <hb> FORGET` erases it. A failed calibration leaves the motor uncalibrated until the next LINK reloads the saved one.
- Closed-loop plan agreed with the owner: step 2 = position moves (run for degrees / go to position, trapezoid profile, then brake / coast / hold, "done" events so blocks can wait or not), step 3 = stall detection + blocks (speed in % of top speed, a "wait" checkbox on move blocks + "wait until done" / "done?"; a "motor profile" block to type the calibration numbers). Later: optional supply voltage measurement (ADC + divider) to scale the feedforward; steppers (28BYJ-48 + ULN2003, 4-pin half-step) generated on the ESP32 with the same move blocks.
- Blocks: `esp32io_*`, toolbox "ESP32 io" → Config / Input / Output / Misc; pin shadows `esp32io_pin`, `esp32io_pin_out`, `esp32io_pin_adc`, `esp32io_pin_dac` (field `ESPPIN`). Generators share `esp32ioStatement()` / `esp32ioReporter()`. STOP reaches the driver through `stopAllMotors`.
- Verified on hardware (owner's tests): connect, BLE round trip ~31 ms (Windows keeps a 30 ms connection interval), picker marker filter, rename, limit switch (`switch_no`), rotary encoder X1 / X2 / X4 (24 steps), L9110S forward / reverse / PWM, DRV8833 + N20 motor with encoder (1:100, 7 ppr) including brake vs coast, MX1508 (1508S board), SG90 180° (angle block) and SG90 360° (speed block, both directions), `tcrt5000` preset with a TCRT5000 and a Keyes IR obstacle sensor (both LOW = object seen), blocks including "wait until encoder degrees ≥ 360". Not yet verified: closed-loop motors (firmware v2: LINK, CAL, RUN, MPAR; only simulated), DAC, analog in, `ir_barrier` preset with a real break-beam sensor, L298N / L293D / TB6612 / ZK-5AD, watchdog, ESP32-S3.

## Blockly 12.4.1 gotchas (loaded from unpkg in index.html)
- The core build has NO `text_multiline` block and no `Blockly.FieldMultilineInput`. Using `text_multiline` in the toolbox crashes every flyout. Multi-line text comes from the plugin `@blockly/field-multilineinput@6.0.2` (script tag in index.html) through the custom `spike_code` block (`getMultilineFieldClass()` in lego_blocks.js, with a safe single-line fallback).
- `Blockly.registry.getClass()` logs a console warning for anything not registered: check `hasItem()` first.
- Never put a block type in the toolbox before checking it is defined: one unknown type empties the whole toolbox.
